> 状态：当前执行手册
>
> 决策日期：2026-07-26
>
> 上位规则：[`project-principles.md`](project-principles.md)
>
> 当前任务：[`next-work.md`](next-work.md)

## 1. 目的

本文定义 HarmoTTY 从私有开发仓库转为公开开源项目时的边界、顺序、验证方法和
GitHub 协作策略。

公开源码的目标是：

- 让用户能够查看、构建、审计和依法修改 HarmoTTY；
- 让外部 Bug 修复、兼容性改进、测试和文档改进能够回流；
- 保留 AGC 提审版本的完整来源、签名和产物证据；
- 不把内部构建缓存、私有环境、签名材料和调查流水一并公开；
- 不因为开放协作而扩大产品功能范围或制造第二份路线图。

本文是执行方法，不维护完成状态。所有待办和完成证据只写入
[`next-work.md`](next-work.md)。

## 2. 已确定的公开模型

### 2.1 仓库与来源权威

采用“私有审计归档 + 干净公开基线”模型，不直接把当前私有仓库原样切换为公开。

| 阶段 | 来源权威 | 用途 |
|---|---|---|
| AGC `1.0.0` 提审审计 | 当前私有仓库的准确提交和仓库外发布归档 | 证明提审产物来自哪份源码 |
| 首次公开 | 从提审源码生成的干净公开基线 | 公开必要源码、测试、构建手册和许可证 |
| 公开后 | 公开仓库 `wandcs/harmotty` | `1.0.1+` 开发、Issue、PR、tag 和 Release |

当前私有仓库在公开前规划改名为仅用于审计的私有归档；执行时先确认目标名称没有
冲突，再释放 `wandcs/harmotty` 作为公开仓库地址。私有归档不得继续接收普通开发
提交。

首次公开提交使用经过审查的干净源码快照，不保留当前 107 个内部开发提交。这样既
避免公开构建缓存和内部环境痕迹，也避免为了清理历史而破坏 AGC 提审证据。

### 2.2 公开内容

公开仓库保留：

- ArkTS、Rust、Web terminal 和资源源码；
- ARM64 HarmonyOS PC 构建、测试和开发脚本；
- 当前有效的产品原则、构建手册、贡献规则和发布说明；
- 能在公共环境运行的自动化测试；
- Apache-2.0 项目许可证、第三方声明和实际分发资源所需许可证；
- 公开 Issue、PR 和安全报告所需模板。

公开仓库不包含：

- 生产或测试签名证书、keystore、profile、密码和本地签名注入文件；
- 已签名 HAP/APP、AGC 提交包或仓库外生产归档；
- `target`、`node_modules`、Hvigor 缓存、构建目录和性能原始产物；
- 已停止支持的 x86_64 native 二进制和只服务旧模拟器的产物；
- 私网 IP、HDC 序列号、个人用户目录、个人邮箱或机器专用绝对路径；
- 只用于内部排障的完整日志、临时实验和已经失效的执行流水；
- GitHub token、Actions secret、部署密钥或个人 SSH 配置。

### 2.3 开源不等于无限支持

Apache-2.0 允许他人复制、修改和分发代码，但 Fork、第三方构建和第三方商店包不属于
HarmoTTY 官方发布。官方身份以维护者账号、官方仓库、官方签名和官方商店页面共同
确认。

公开仓库不承诺：

- 合并所有 PR；
- 实现所有 Feature Request；
- 对 Issue 提供固定响应时限；
- 支持 HarmonyOS PC 之外的设备；
- 为 Fork、修改版或第三方签名包提供支持。

## 3. 不可跨越的安全边界

### 3.1 AGC 提审证据先冻结

任何仓库改名、历史重建或可见性变更前，必须保存：

1. 提审源码的完整 commit SHA；
2. `git status`、分支和远端状态；
3. HAP、APP、native `.so` 和 manifest 的 SHA-256；
4. HAP/APP 签名和 digest 验证结果；
5. 生产签名材料位于仓库外的确认；
6. 包含全部私有 refs 的离线 Git bundle；
7. 私有归档的保存位置、负责人和恢复方法。

公开提交需要增加来源映射，说明：

- 私有 AGC 提审 commit；
- 首次公开 commit；
- 从公开快照排除的路径和理由；
- 应用构建输入是否发生变化；
- 若发生变化，为什么不会把公开快照错误描述成提审产物的精确源码。

### 3.2 公开是不可逆的信息披露

仓库一旦公开，应假定任何内容已经被第三方克隆。后续删除仓库、删除文件或重新改为
私有，都不能收回已经产生的 Fork 和本地副本。

因此，出现以下任一情况时不得公开：

- secret 扫描有未处置发现；
- AGC 提审源码或产物哈希没有冻结；
- 公开树仍包含本地目录、设备标识或私网地址；
- 许可证、品牌或第三方资源归属不清楚；
- 公开 CI 会在个人自托管机器上运行陌生 Fork 的代码；
- `SECURITY.md` 仍提供无效的私密报告渠道。

若公开后发现秘密，第一动作是撤销或轮换秘密，而不是只删除 Git 文件。

## 4. 分阶段执行

### 4.1 阶段 A：冻结提审来源

输入是当前私有仓库和已提交 AGC 的生产产物。

执行：

1. 重新确认提审对应的准确源码 SHA，不能从当前 `HEAD` 猜测；
2. 对照 release manifest 核对所有产物哈希和签名状态；
3. 创建并离线保存包含全部 refs 的 Git bundle；
4. 记录私有仓库当前 Issues、PR、Actions、artifacts、releases 和设置；
5. 标记哪些记录只属于内部审计，不能迁移到公开仓库。

阶段门槛：

- 可以从私有归档恢复提审源码；
- 可以独立核对提审 HAP/APP；
- 后续公开仓库操作不会改变或覆盖这份证据。

### 4.2 阶段 B：建立干净公开基线

从已冻结的源码提交导出新工作目录，在新 Git 历史中建立公开基线。不要在当前发布
工作区中执行历史重写。

公开树至少清理：

- `harmotty_ssh/size-lab/**/target*`；
- `tools/node_modules/`；
- `entry/libs/x86_64/libharmotty_ssh.so`；
- 旧 x86_64 构建产物和不再支持的模拟器发布入口；
- 测试截图、日志、性能原始数据和本地缓存；
- `.codex/config.toml` 等仅服务单机沙箱的配置；
- 重复、过期或包含机器专用路径的 agent 指令；
- 归档文档中的私网地址、设备序列号、个人路径和已失效实现说明。

`.gitignore` 至少覆盖所有层级的：

```gitignore
**/node_modules/
**/target/
**/build/
```

生成目录即使已被 ignore，只要仍受 Git 跟踪也必须从公开树移除。

公开树中的构建脚本必须使用仓库相对路径、参数或可发现的工具位置；不得依赖个人
用户目录或固定的本机 checkout 绝对路径。

阶段门槛：

- 新仓库只包含公开所需内容；
- `git ls-files` 不再列出缓存和不支持的 native 二进制；
- 从干净 clone 可以进入公开文档描述的构建路径；
- 公开快照与 AGC 来源的差异有完整分类。

### 4.3 阶段 C：补齐公开文档与治理

需要审查或建立：

| 文件 | 要求 |
|---|---|
| `README.md` | 说明 AGC/发布状态、PC-only 范围、构建限制、官方发布和贡献入口 |
| `LICENSE` | 保持 Apache-2.0，版权表述和包元数据一致 |
| `THIRD_PARTY_NOTICES.md` | 与实际 vendored 资源和锁文件一致 |
| `SECURITY.md` | 支持版本正确；只提供真实可用的私密报告渠道 |
| `CONTRIBUTING.md` | 以项目原则为准，说明公共 CI 与真机门禁、贡献许可和范围边界 |
| `CODE_OF_CONDUCT.md` | 接受外部贡献时采用清楚、可执行的行为规则 |
| `SUPPORT.md` | 区分 Bug、使用咨询、安全问题、非官方 Fork 和非支持平台 |
| `TRADEMARKS.md` | 明确 HarmoTTY 名称、图标、官方包和官方签名的使用边界 |
| Issue/PR 模板 | 收集可复现证据，提醒脱敏，不制造功能承诺 |

项目暂不引入 CLA。`CONTRIBUTING.md` 和 PR 模板明确：贡献者必须有权提交代码，
被接受的贡献按项目 Apache-2.0 许可证进入项目。出现公司级贡献或权属争议后再讨论
DCO 或 CLA，不提前增加贡献摩擦。

仓库、Cargo、OHPM、README、Issue 模板和 Release 中的 canonical URL 必须统一为
最终公开地址。

阶段门槛：

- GitHub community profile 的核心文件齐全；
- 安全报告不会进入公开 Issue；
- 用户能够区分官方包与 Fork；
- 文档不会暗示手机、平板或 x86_64 受支持。

### 4.4 阶段 D：建立可信的公共 CI

公共 PR 自动化只运行不需要秘密、签名材料和个人设备的检查。

建议的公共检查：

1. `git diff --check` 和源码控制策略；
2. PowerShell 脚本语法检查；
3. Web terminal policy 测试；
4. Rust `cargo fmt --check`；
5. 能在 GitHub-hosted runner 稳定链接的纯 Rust core 测试；
6. 依赖、许可证和 vendored 资源一致性检查；
7. secret scan；
8. GitHub Actions 与依赖更新检查。

ArkTS/HAP、ARM64 native 集成和真实 HarmonyOS PC 交互仍属于维护者门禁。公共 CI
不得用打印提示代替实际检查，也不得把不可运行的检查标为成功。

Fork PR 安全规则：

- Actions 默认 `contents: read`；
- 不向 Fork PR 暴露 secrets；
- 不使用 `pull_request_target` 检出并运行陌生提交；
- 不在连接个人文件、签名或真机的长期自托管 runner 上运行陌生 PR；
- 需要 DevEco 或真机的验证只由维护者在确认代码可信后触发。

阶段门槛：

- 所有 required checks 都执行真实验证；
- 陌生 Fork 无法读取秘密或控制个人设备；
- CI 失败信息能够指导贡献者修正问题。

### 4.5 阶段 E：公开前干跑

在独立目录中模拟匿名用户：

1. 从候选公开仓库进行全新 clone；
2. 检查 tracked 文件数量、最大文件和对象体积；
3. 搜索个人路径、私网地址、设备序列号和占位联系方式；
4. 使用 Gitleaks 扫描当前树和全部公开 refs；
5. 使用第二种扫描器或 GitHub secret scanning 复核高风险发现；
6. 执行公共 CI 的全部命令；
7. 在维护者环境执行 `tools/verify-pc.ps1 -SkipDevice`；
8. 核对 README、许可证、第三方声明和相对链接；
9. 比较公开快照与 AGC 来源映射。

如果公开基线包含构建相关修改，应在开发目录完成正常 ARM64 验证；如果包含
设备可见行为修改，还必须重新执行真机验证。纯仓库清理和文档修改不得冒充产品行为
验证。

阶段门槛：

- secret 扫描没有未处置发现；
- 公共检查全部通过；
- 干净 clone 可重复；
- AGC 提审产物没有被重新构建、替换或重新描述。

### 4.6 阶段 F：建立公开 GitHub 仓库

所有 GitHub 写操作前先确认：

```powershell
gh auth status
```

活动账号必须是 `wandcs`。如果认证无效，先恢复认证，不使用浏览器自动化绕过。

按以下顺序执行：

1. 完成私有归档和离线 bundle；
2. 确认计划使用的私有归档名称没有冲突；
3. 释放 `wandcs/harmotty` 公开地址；
4. 推送干净公开基线；
5. 设置仓库描述、topics、许可证和默认分支；
6. 配置 Issue、PR、security 和 Actions；
7. 配置 `main` ruleset；
8. 从未登录环境验证匿名访问和 clone；
9. 最后宣布源码公开。

不要在同一操作窗口里同时做生产发布、签名轮换或产品代码修改。

AGC 审核期间可以先公开源码，但 README 必须准确写成“审核中”，不能暗示商店版本已经
上架。`v1.0.0` tag 和 GitHub Release 只有在提审来源映射、正式产物哈希和发布状态
核对完成后才能建立；如果 tag 位于新的公开 commit，Release 必须同时记录其对应的
私有 AGC commit。

### 4.7 阶段 G：公开后观察

首次公开后至少检查：

- Actions 是否按预期运行；
- Issue 和 PR 模板是否正确显示；
- Private Vulnerability Reporting 是否可用；
- Dependabot、secret scanning 和 push protection 是否开启；
- ruleset 是否确实阻止直接破坏 `main`；
- README、release、Cargo 和 OHPM 链接是否指向公开仓库；
- 是否出现需要立即处理的许可证、安全或身份冒用问题。

公开后的 Bug 修复进入正常版本流程。与产品原则冲突的 Feature Request 直接说明范围
边界，不因公开而改变产品方向。

## 5. GitHub 协作策略

### 5.1 功能开关

| 能力 | 首次公开设置 | 规则 |
|---|---|---|
| Fork | 接受 | 公开仓库的正常能力；Fork 不是官方发行 |
| Pull Request | 开启 | 接受 Bug、兼容性、测试和文档贡献 |
| Issues | 开启 | 接受 Bug、兼容问题和文档问题 |
| Feature Proposal | 开启但严格分流 | 必须通过项目原则中的功能取舍问题 |
| Private Vulnerability Reporting | 开启 | 安全漏洞不得进入公开 Issue |
| Discussions | 关闭 | 有持续社区讨论需求后再开启 |
| Wiki | 关闭 | 当前文档继续保存在仓库 |
| Projects | 关闭 | `next-work.md` 保持唯一工作清单 |

### 5.2 Issue 到工作项的边界

Issue 是外部输入，不是自动成立的项目 TODO。

处理顺序：

```text
Issue / PR
  → 复现与信息补全
  → 按 project-principles.md 判断范围
  → 接受、拒绝、等待证据或标记重复
  → 只有接受的工作才进入 docs/next-work.md
  → 实现、验证和关闭
```

Bug 模板至少收集：

- HarmoTTY 版本和来源；
- HarmonyOS PC 型号和系统版本；
- SSH server 类型；
- 最小复现步骤；
- 期望和实际行为；
- 已脱敏的日志；
- 是否能在当前官方版本复现。

模板必须提醒删除：

- 用户名、主机名、IP 和端口；
- 私钥、公钥全文、密码和 passphrase；
- known_hosts 私有环境内容；
- HDC 序列号和个人目录；
- 公司内部服务器和业务数据。

Feature Proposal 必须回答：

1. 它阻断了哪条核心终端路径；
2. 影响是否频繁且可复现；
3. SSH 标准、`.ssh/config`、HarmonyOS 或远端工具为什么不能解决；
4. 会增加哪些长期概念、状态、入口和故障模式；
5. 是否存在更小、更局部的解决办法。

### 5.3 PR 合并规则

PR 应当：

- 说明解决的问题和范围；
- 关联 Issue，或解释为什么是无需 Issue 的小修复；
- 遵守 `project-principles.md`；
- 提供相关自动化验证；
- 明确是否需要 ARM64 构建或真实 PC 验证；
- 不包含签名材料、真实服务器信息或生成缓存；
- 允许维护者在必要时要求缩小范围或拆分。

`main` 建议只保留 squash merge，合并后删除来源分支。单维护者阶段要求通过 PR 和
required checks，但不强制另一个外部维护者批准；维护者仍通过 PR 留下审查和验证
记录。出现共同维护者后再要求至少一个批准。

维护者可以拒绝：

- 超出 PC-only SSH 终端定位的功能；
- 为假想扩展增加抽象、依赖或公共框架；
- 没有复现证据的行为改动；
- 不能在目标环境验证的核心交互改动；
- 大量无关格式化、生成文件或混合重构。

### 5.4 分支和安全设置

`main` ruleset 至少要求：

- 通过 Pull Request 更新；
- required checks 成功；
- 禁止 force push；
- 禁止删除；
- 保持可追踪的提交历史；
- 维护者仅在明确的紧急修复中使用 bypass，并补充事后记录。

Actions：

- 默认 workflow token 只读；
- 不允许 Actions 创建或批准 PR；
- 第三方 Action 优先固定到完整 commit SHA；
- Dependabot 分别维护 Actions、Cargo 和 npm 依赖，OHPM 依赖由单独检查核对；
- 不把自托管设备 runner 作为公开 PR 的自动执行目标。

## 6. 品牌、许可证和官方发布

项目代码继续使用 Apache-2.0。第三方资源按各自许可证分发。

在首次公开前明确：

- “HarmoTTY”名称和图标是否作为项目标识保留；
- Fork 在什么条件下必须改名和更换图标；
- `com.harmotty.app` 包名不得被第三方描述为官方包；
- 只有 `wandcs` 发布、官方签名和官方商店页面共同构成官方发行；
- GitHub Release 中提供的哈希、manifest 和许可证归档如何与 AppGallery 包对应。

品牌规则不能修改 Apache-2.0 授予的代码权利，但可以避免第三方修改版冒充官方应用。
涉及正式商标注册或法律承诺时，由维护者另行获得法律意见。

## 7. 首次公开完成标准

只有同时满足以下条件，才能宣布源码已公开：

1. AGC 提审源码、产物、签名验证和哈希已冻结；
2. 私有历史可以恢复，但不再作为普通开发仓库；
3. 公开仓库从干净基线开始；
4. 当前树和公开历史没有未处置的秘密；
5. 当前树没有生成缓存、x86_64 native 产物或个人环境痕迹；
6. README、SECURITY、CONTRIBUTING、支持边界和品牌规则一致；

## 8. 回退原则

在正式公开前，任一阶段都可以停止并保留私有仓库，不需要为了日期强行继续。

正式公开后：

- 普通文档或 CI 问题通过公开 PR 修复；
- 许可证或来源问题暂停发布并补充声明；
- 秘密泄露立即轮换秘密、清理历史并发布安全说明；
