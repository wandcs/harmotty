# HarmoTTY 产品与技术原则

> 状态：项目基础规则；生效日期：2026-07-18

本文档定义 HarmoTTY 的产品边界、功能取舍和技术设计原则。它不是某个版本的需求清单，而是需求、设计、实现、评审和重构共同遵循的长期规则。

当其他当前文档、历史方案或局部实现与本文冲突时，以本文为准。`docs/archive/` 中的材料只用于追溯，不能作为新增功能或复杂度的直接依据。

## 一、产品定位

**HarmoTTY 是为 HarmonyOS PC 设计的、键盘优先、开箱即用的可靠远程终端。**

“鸿蒙 PC 的 Ghostty”表示对产品品质和设计哲学的参照，不表示复制 Ghostty 的功能清单。HarmoTTY 借鉴的是终端应当原生、快速、安静、可靠的理念，并将其用于 HarmonyOS PC 的远程终端场景。

当前产品边界：

- 只面向 ARM64 HarmonyOS PC 和键鼠场景。
- 以 SSH 连接远端环境，不提供本地 shell 或 Linux 环境模拟。
- 产品心智是终端；SSH 是连接远端终端的实现方式。
- 不以功能数量、设置数量或可扩展性作为产品竞争目标。

## 二、三项最高原则

原则按以下顺序处理冲突：

1. **可靠是底线。**
2. **简洁是默认选择。**
3. **易用只优化核心路径。**

### 2.1 可靠

- 终端输入、输出、尺寸、焦点和状态必须正确且可预测。
- 连接、认证、主机校验、取消、断线和重连必须有确定行为。
- Tab、Pane、Session 之间不得串状态、串输出或隐式共享所有权。
- 密钥、主机指纹、远端标题、剪贴板和 Bridge 必须有明确安全边界。
- 失败必须可观察、可理解、可恢复，不能表现为无响应。
- 涉及真实交互和生命周期的行为必须在目标鸿蒙 PC 上验证。

可靠性所必需的复杂度不能因追求代码短小而省略。

### 2.2 简洁

- 减少用户必须理解的概念、入口、模式和配置。
- 减少代码中的状态源、所有者、特殊分支和跨层协调。
- 同一任务保留一条清楚的主路径，不并存多套等价操作模型。
- 优先复用 SSH 和 HarmonyOS 标准，不自建平行的数据模型。
- 不为假想需求提前建设扩展点、插件层、通用框架或兼容层。
- 删除已经失去价值的功能和抽象，视为正常维护而不是功能倒退。

界面元素少并不自动等于简洁；如果隐藏界面导致状态更难理解或操作更不稳定，应优先保证可靠和清楚。

### 2.3 易用

- 打开应用后应尽快进入可工作的终端路径。
- 高频操作应直接、可发现，并具有稳定的键盘行为。
- 默认值应适合大多数用户，避免把必要决策转嫁给用户。
- 错误信息应说明发生了什么，以及用户下一步可以做什么。
- 低频高级需求优先由 `.ssh/config`、`known_hosts` 或远端工具解决。
- 不为少量用户或偶发体验增加永久入口、长期状态和维护负担。

## 三、功能取舍规则

任何新增功能、设置、交互模式或兼容逻辑，必须依次回答：

1. 它是否直接服务“连接远端并完成终端工作”的核心路径？
2. 不做它，目标用户是否会频繁受阻，而不仅是少一点方便？
3. SSH 标准、HarmonyOS 系统能力或远端工具是否已经能够解决？
4. 它会增加哪些永久概念、状态、入口、依赖和故障模式？
5. 删除它以后，产品是否仍然完整成立？
6. 它能否用更小、更局部、没有新概念的方式解决？

默认决策：

- 核心路径上的正确性、安全性和可恢复性问题：必须做。
- 高频需求且能保持现有模型简单：可以做。
- 仅有假想用户、低频收益或需要长期架构负担：不做。
- 有价值但证据不足：记录问题，不提前实现。

不能只用“Ghostty 有”“以后可能扩展”“实现起来不难”作为加入功能的理由。

### 3.1 应长期做好的能力

- SSH 连接、认证、主机指纹、取消、断线和重连。
- 正确、流畅的终端输入输出和常见 TUI 兼容。
- 键盘、焦点、复制、粘贴、搜索和窗口尺寸体验。
- 少量 Tab 和最多双 Pane 的清楚并行模型。
- 明确的连接状态、错误信息和恢复路径。
- 少量必要设置，例如字号、主题和窗口状态。
- 与 HarmonyOS PC 窗口、剪贴板、主题和生命周期的自然集成。

### 3.2 默认不进入产品范围的能力

- GUI 主机资产管理和自建主机数据库。
- SFTP 文件管理器、本地 shell、包管理器或 Linux 环境模拟。
- AI、协作、审计、堡垒机和共享会话平台。
- 插件系统、宏系统、脚本平台和为扩展而设计的公共框架。
- 无限分屏、复杂工作区布局和多套会话组织模型。
- 大量皮肤、主题以及低价值外观设置。
- 只为少数程序服务且维护成本高的终端协议扩展。
- 手机、竖屏和为非 PC 设备引入的响应式复杂度。

命令面板、自定义快捷键、会话恢复、多窗口等灰区能力，不自动进入路线图；只有出现明确、持续的核心场景证据后才重新评估。

## 四、技术原则

### 4.1 先明确所有权，再讨论分层

项目的核心领域模型固定为：

```text
App Shell
  └─ Tab → Pane → Session
                 ├─ SSH Transport
                 ├─ Terminal Surface
                 └─ System Services
```

- Tab 拥有 Pane，Pane 通过稳定标识拥有一个 Session。
- Session 是连接生命周期和终端交互的业务边界。
- 不用数组相邻关系、当前索引、WebView 实例或 UI 状态隐式表达所有权。
- 每项可变状态必须有一个明确的唯一权威来源。

### 4.2 边界按职责存在

- **App Shell**：窗口、Tab、Pane、焦点和少量全局设置。
- **Session**：连接、认证、主机校验、断线、取消和重连状态机。
- **SSH Transport**：Rust/russh、PTY 和字节流，不决定 UI 文案或界面行为。
- **Terminal Surface**：ArkWeb/xterm 的显示、输入、选区和 resize，不管理业务状态。
- **System Services**：剪贴板、Preferences、窗口等 HarmonyOS 能力。
- **UI**：渲染状态并发送用户意图，不跨越边界编排多个底层对象。
- **Bridge**：只承载经过验证的协议消息，不承担业务规则或修补终端内容。

允许为保持这些真实边界而调整目录分层；`Page → ViewModel → Model → Common` 是依赖方向参考，不得凌驾于清楚的状态所有权之上。

### 4.3 不为架构而架构

只有满足至少一项时才新增类型或抽象层：

- 拥有独立状态或生命周期。
- 封装明确且可测试的策略。
- 隔离真实的平台、进程或协议边界。
- 显著简化核心状态机或消除重复规则。

单一实现、没有替换需求的接口，纯转发的 Manager/Service，以及仅为缩短文件而进行的拆分，默认不增加。局部、直接、可测试的代码优于形式完整但需要跨文件追踪的架构。

### 4.4 控制复杂度的方向

- 业务规则与传输、渲染、平台适配分离。
- 结构化事件和状态优于由 UI 文案、字符串片段或时序猜测状态。
- 一个行为只有一个实现入口；不要在 ArkUI、WebView 和 Rust 三处分别修补同一规则。
- 优先删除特殊分支和重复状态，再考虑增加缓存、保留机制或补偿逻辑。
- 性能优化必须有测量证据，并且不能破坏正确性或明显增加维护复杂度。
- 新依赖必须解决明确问题；能够用平台能力或少量代码完成时不引入依赖。

### 4.5 验证是设计的一部分

- 自动化测试证明状态机、协议和纯逻辑。
- ARM64 构建证明目标平台代码能够集成。
- 真机验证证明焦点、键盘、剪贴板、窗口、持久化、终端交互和 SSH 生命周期。
- 编译通过不能替代行为验证，安装启动也不能替代交互验证。
- 修复应验证真实事件链，而不是只验证最终表象。

## 五、变更治理

- 需求、方案和代码评审必须说明其如何符合本文原则。
- 引入新概念、长期状态、依赖或跨层路径时，必须说明为什么现有模型无法解决。
- 与本文冲突的需求不能通过局部实现静默落地；应先讨论并明确修改本文。
- 修改本文属于项目方向变更，应记录动机、替代方案和预期长期成本。
- 版本计划和旧愿景必须服从本文，不能用路线图倒逼原则让步。

最终判断标准：

> **HarmoTTY 不追求成为功能最多的鸿蒙终端，而要成为最不打扰用户、最少出错、打开就能工作的那个。**
